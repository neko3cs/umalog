# 競馬メモアプリ 企画書

**アプリ名: Umalog（ウマログ）**
（サブタイトル案: 「Umalog — 予想と収支の競馬メモ」など。「競馬」の説明語はサブタイトル側で補う想定）

個人利用を目的とした、競馬（中央・地方を問わない）の予想・収支を記録するiOSアプリの設計方針まとめ。

---

## 1. 概要

- **目的**: 個人の予想印・購入金額・メモを記録するメモ／予想記録ツール。
- **対象**: 自分専用（パーソナルユース）。
- **重要な前提**: 馬券購入・賭けの仲介・送金などの機能は**一切持たない**（自己完結した記録アプリ）。
- **対応範囲**: 手入力・データ連携なしのため、**中央（JRA）・地方（NAR／南関東等）を問わず**記録可能（理屈上は海外競馬も可）。
- **プラットフォーム**: iOS（ネイティブSwiftUI）。

---

## 2. 差別化・コンセプト

競馬の記録・収支管理アプリは既に複数存在し、レースデータ内蔵・クラウド同期・自動入力などで**利便性を高めた先行アプリ**が多い。本アプリは手入力中心のため、利便性ではそれらに劣る。したがって勝負する軸は利便性ではなく、以下の3点に置く。これらはすべて「**ローカル完結**」という1点から自然に導かれる一貫した強み。

**差別化の3本柱:**

1. **ローカル完結・プライバシー重視（＋OSS）**
   - デフォルトはデータを端末内のみに保持。アプリ独自のアカウント不要・開発者によるデータ収集なし。
   - iCloud同期は**任意（デフォルトOFF）**。オンにしても同期先は**ユーザー自身のプライベートiCloudのみ**で、開発者は一切アクセスできない（自前サーバーを持たない）。
   - 収支は金銭情報なので「（少なくとも開発者には）預けない」価値が大きい。
   - 公開リポジトリ（オープンソース）にすることで「開発者がデータを集めていない」ことを技術的に示せる。
   - 先行アプリの多くはアカウント＋クラウド前提のため、「デフォルト完全ローカル＋同期は任意・自分のiCloudのみ」は明確な違いになる。

2. **収支の自動計算（日／月／年）**
   - メモ・予想記録に寄せたアプリは収支・回収率までカバーしないことが多く、収支は別アプリで補う構図になりがち。
   - 予想印・メモと収支集計を**1本に統合**する点が差別化。

3. **完全無料・無制限**
   - 先行アプリにはフリーミアム型（無料版に保存件数などの上限があり、解除に月額課金）が多い。
   - 本アプリはローカル完結でサーバーコストがほぼ無いため、**無料・無制限**を無理なく成立できる。

**副次的な強み（手入力ゆえの利点）:**

- **中央・地方の両対応**: 自分で入力するため、中央（JRA）でも地方（NAR／南関東等）でも区別なく記録・収支計算できる。データ内蔵型のアプリは「中央のみ対応」になりがちな一方、手入力アプローチなら種別を問わず対応できる隠れた優位点。

**トレードオフ（正直な整理）:**

- データ連携型の強み（自動データ入力・クラウド同期・複数端末）は本アプリにはない。
- 本アプリの「無制限」は「手入力データを1端末でローカルに無制限に貯められる」という意味。
- 棲み分け: 利便性（自動データ・同期）を取るか、自由度（無料・無制限・プライバシー）を取るか。
- 「広告なし」自体は珍しくない（サブスク型の競合は元々広告を出していない）ため、単独の差別化ではなく無料訴求の一部として扱う。

**ターゲット:** 自分自身。加えて「無料・広告/課金なし・データを外に出さない・収支まで自分で管理したい」というプライバシー志向の手動派ユーザー。

## 3. 機能要件

| 機能 | 内容 |
|------|------|
| レース情報の登録 | 出走馬・馬場状態・コース情報を記録（中央・地方問わず／取得方法は下記） |
| 予想印 | ◎ ○ ▲ △ ☆ 注 押 消 の8種をタップで入力 |
| 購入金額メモ | 馬券の購入金額を記録（テンキー入力） |
| 払戻金の記録 | 的中時の払戻金（回収額）を記録（収支計算に必要） |
| 収支の自動計算 | 購入金額と払戻金から、**日間・月間・年間**の収支を自動集計・表示 |
| Markdownメモ | レースや予想に対する自由メモをMarkdownで記述 |
| iCloud同期（任意） | ユーザー自身のiCloudへ同期・バックアップ（デフォルトOFF・開発者はアクセス不可） |
| CSVエクスポート | 記録データをCSVで書き出し（他アプリへの移行・表計算での閲覧・持ち出し用） |
| お布施（任意課金） | 機能は一切ゲートしない任意のチップ。IAP（消耗型）を主、GitHub経由のOSSリンクを補助（詳細は9章） |

> **補足**: 「収支の自動計算」を成立させるには、購入金額だけでなく**払戻金（回収額）の記録**が必須。このため上記に払戻金の記録機能を追加している。集計は「払戻金の合計 − 購入金額の合計＝収支」を、日／月／年の各期間で算出する。

## 4. 設計上の決定事項

### 4.1 データの取得方法 → 手動入力を基本とする

自動取得の選択肢を検討した結果、いずれも壁があったため**手動入力**を採用。

- **JRA-VAN データラボ（公式）**: 月額制（有料）かつ **Windows専用** のため、Mac/iOSから直接利用できない → 不採用。
- **スクレイピング（netkeiba等）**: 無料だがサイト改修で壊れやすく、利用規約の確認も必要 → 基本不採用。
- **OCR（写真/スクショ）**: 日本語対応はあるが密な表で誤認識が出やすく不安定 → 不採用。
- **AIによる解析**: 使わない方針。
- **JRA公式アプリからのコピペ**: ネイティブアプリは表のテキスト選択・コピーが基本的に不可 → 不可。

**入力を楽にする工夫**（手入力の負担を最小化）:

- **オートコンプリート**: 入力した馬名・騎手・調教師を端末内に蓄積し、次回から数文字で候補表示。
- **共通項目の引き継ぎ**: 馬場状態・コース・開催場は1日の全レースで共通のため、一度設定したら各レースに継承。
- **入力部品の最適化**: 頭数を決めれば行を自動生成、テンキー・タップ中心で打鍵を削減。
- **競馬場プリセット（中央・地方を最初から同梱）**: 中央10場に加え、地方競馬場（大井・船橋・川崎・浦和・園田・姫路・門別・名古屋・笠松・高知・佐賀 等）も最初からプリセットに含める。実装はリストに項目を足すだけで手間が小さいため、検討事項ではなく確定とする。
- **券種は自由入力／編集可**: 固定リストに限定せず、追加・編集できる方式にして、中央・地方の券種や呼称差にそのまま対応する。

> **補助手段として検討中**: JRAの**Webサイト（sp.jra.jp）**の出馬表はHTMLなので文字を選択コピーできる。これを貼り付けてルールベースで解析（パース）すれば打鍵を大幅に減らせる。これはAIでもOCRでもなく決定的な文字列処理。ただしJRA側のページ改修時にパース規則の調整が必要になる軽い保守が発生する。「保守を避けたい」方針を重視するなら、まずは完全手入力（外部形式に非依存・保守不要）で始め、必要に応じてコピペ補助を後付けする。

### 4.2 予想印の入力

- 使用する印は **◎ ○ ▲ △ ☆ 注 押 消 の8種**。
- 各馬に対し、これらをタップで選べるセグメント／ボタンUI。
- **1頭につき予想印は1つだけ（複数付与は不可）**。
- 出走馬の並び順は**入力順がデフォルト**。加えて**ソート機能も実装**する（例: 馬番順・予想印順など）。

### 4.3 購入金額

- テンキー（数値キーボード）入力でメモ。

### 4.4 メモ

- Markdownで自由記述。

### 4.5 データの持ち出し（CSVエクスポート）／バックアップ方針

- **バックアップ・復元は主に「iCloud同期（任意）」が担う**（4.8参照）。そのため、当初想定していた「バイナリで往復するだけのバックアップ」は役割が薄くなる。
- 代わりに**エクスポートはCSV形式**とし、用途を「**他アプリへの移行・表計算での閲覧・データの持ち出し**」に置く。ユーザーを囲い込まず、いつでも自分のデータを持って出られる——という本アプリの透明性・プライバシー思想と一貫する。
- **CSVと関係データの注意**: データは関係構造（レース—出走—馬券）を持つため、CSVは平坦化が必要。実装方針として「エンティティごとに複数CSV（races / entries / bets …）」または「閲覧用に非正規化した1枚のCSV」のいずれかを選ぶ。持ち出しが主目的なので前者寄りが無難。
- **CSVインポート（取り込み）は best-effort**。完全な復元はiCloud同期に任せ、CSV取り込みは「他から持ち込む補助」と位置づける（関係構造の完全再構築までは保証しない）。

### 4.6 馬券と収支の扱い

- **レースと馬券は1対多（レース1 — 馬券n）**。1レースに複数の馬券を記録できる（馬券が記録の単位）。
- 収支集計は**レース日を基準**に行う。
- 未確定（結果待ち）の馬券は**払戻金0円**として扱う。
- **回収率（払戻合計 ÷ 購入合計）を表示**する。
- 任意期間／会場／券種でのフィルターは**課題事項（後回し）**。

### 4.7 データモデル・画面構成 → Claude Codeがコードベースで設計

- データモデル（スキーマ）と画面構成は、本メモの方針に沿って**Claude Codeにコードベースで設計**させる（本メモ側では細部を固定しない）。
- ただし以下の制約は必ず満たすこと: 「レース1 — 馬券n」「予想印は1頭1つ」「収支はレース日基準・未確定は払戻0円・回収率を表示」「SwiftDataで永続化」「CSVで持ち出せる」。
- **iCloud同期（任意）に備え、データモデルは最初からCloudKit互換で設計する**: ①ユニーク制約（`@Attribute(.unique)`）を使わない ②全プロパティはオプショナルかデフォルト値を持つ ③全リレーションシップはオプショナル ④順序付きリレーションは使わず、並び順は数値フィールド（例: `sortIndex`）で表現する ⑤CloudKit有効化後はスキーマ変更が軽量マイグレーションの範囲に限られる点に留意。後付けは非常に苦しいため初期設計から考慮する。
- 画面はおおよそ「一覧 → レース詳細 → 入力 → 収支サマリー」を想定（具体はClaude Codeが設計）。

**参考: データモデルの考え方**（Claude Codeへ渡す設計意図。細部は固定せず、SwiftDataのリレーションとして実装させる前提）

- **マスタ**
  - 会場
  - 券種（編集可）
  - （任意）馬・騎手・調教師 … オートコンプリート用
  - 予想印（8種で固定のため、テーブルにせず enum／コード値でも可）
- **トランザクション**
  - レース（日付・会場・レース番号・距離・芝/ダート・馬場状態・中央/地方区分 等）
  - 出走（＝「レース-出走馬」の関連実体。馬番・騎手・予想印・着順 等を持つ。出馬表の1行に相当）
  - 馬券（所属レース・券種・買い目・購入額・払戻額 を持つ）
- **ER（関係）**
  - 会場 1 — レース n
  - レース 1 — 出走 n（かつ 馬 1 — 出走 n。レースと馬の多対多を「出走」が仲介する）
  - 出走 1 — 予想印 0..1（印なしも可。1頭1印）
  - レース 1 — 馬券 n
  - 券種 1 — 馬券 n
- **設計上のポイント**
  - 予想印は「馬」ではなく「そのレースに出走したその馬（＝出走）」に紐づける（同じ馬でもレースごとに印が変わるため）。
  - 多対多（レース↔馬）だけが仲介実体「出走」を必要とする。1対多（会場→レース、レース→馬券 等）は子側がIDを1つ持てばよく、独立した関連テーブルは不要。
  - SwiftDataでは概念上の「関連テーブル」を明示的には作らず、`@Model` 同士のリレーション（参照）で表現する。概念上の「レース-出走馬関連」は、実装では「出走（例: RaceEntry）」という1つのモデルになる。

### 4.8 iCloud同期（任意機能）

- **デフォルトOFF**。ユーザーが設定で明示的にオンにしたときだけ有効化する（プライバシー重視のデフォルトを崩さない）。
- SwiftData標準のCloudKit連携を使い、同期先は**ユーザー自身のプライベートiCloudのみ**（公開／共有DBは使わない）。**開発者はデータにアクセスできず、サーバーも持たない**。
- アプリ独自のログインは不要（iCloudのアカウント認証に依存）。
- **有効化には有料Apple Developerアカウント＋iCloud/CloudKitケイパビリティが必要**。そのため「無料アカウントでのローカル先行開発 → 有料加入後にiCloud同期を実装・実機で検証」という順序で進める（シミュレータでの同期検証は不安定）。
- データモデルのCloudKit互換要件は 4.7 を参照。
- 位置づけ: iCloud同期＝自動・継続的なバックアップ／複数端末同期。CSVエクスポート＝手動・iCloudに依存しない持ち出し／移行。両者は補完関係（可用性・復旧の冗長化）。

## 6. App Store 審査対策

賭けを題材にするジャンルのため、以下を遵守して審査リスクを下げる。

- **「賭け機能はない」と明示**: アプリ説明文＋審査担当向けメモ（App Review Notes）に「個人の予想・収支を記録するツールで、馬券購入・賭けの仲介・送金機能は一切ない」と記載。
- **馬券購入サイトへの導線を入れない**: 即PAT/IPAT等へのリンク・ボタンを置かない（賭けの幇助とみなされるのを回避）。
- **リアルマネーゲーミング規定（ガイドライン5.3.4）の対象外**: アプリ内で賭け・送金を行わないため、免許・地域制限等の厳しい要件には該当しない見込み。ただしジャンル特有の警戒は受け得る。
- **年齢レーティング**: 高め（成人向け＝18+相当）を想定。App Store Connectの「ギャンブルとコンテスト」項目を正直に回答。
- **機能の作り込み**: 機能最小要件（4.2）で「薄い個人アプリ」と見なされないよう、各機能を一通り完成させ、初回起動の説明等も整える。
- **心構え**: 初回審査で質問・差し戻しがあっても、Resolution Centerで「賭け機能のない記録アプリ」と説明すれば対応可能。

## 7. 技術・開発方針

- **UI**: ネイティブSwiftUI。
- **データ保存**: **SwiftData**（確定）で端末内にローカル保存。
- **最小対応OS（deployment target）**: **iOS 18**。理由: iOS 17は全対応端末がiOS 18へ更新可能で実質サポート終了済み、一方iOS 18は現役で保守されており、2018年以降のほぼ全端末をカバーできる。SwiftDataもiOS 17以降で利用可。
- **データモデル・画面構成**: 本メモの制約（4.6 / 4.7）に沿って**Claude Codeにコードベースで設計**させる。
- **プロジェクトの起こし方**:
  - Xcodeで App テンプレート（Interface = SwiftUI / Language = Swift）から空プロジェクトを作成 → 一度シミュレータでビルド確認。
  - 以降の実装はClaude Codeにコード生成を依頼。
  - **`.pbxproj`（Xcodeプロジェクトファイル）はClaude Codeに直接編集させない**（破損リスク）。**新規Swiftファイルの追加はXcodeのGUIから手動**で行う。
- **Claude Code**: ターミナルで動作（API通信型で軽量）。Intel機でも動くが、最新のMac前提で運用。
- **`CLAUDE.md`に書いておく前提**:
  - `.pbxproj`は編集しない／新規ファイルはXcodeから追加する
  - 賭け機能を持たない・自己完結
  - 手入力中心・予想印タップ入力（8種・1頭1印）・Markdownメモ・CSVエクスポート・iCloud同期は任意（デフォルトOFF）
  - SwiftData採用・最小deployment target は iOS 18・データモデルはCloudKit互換（unique制約なし／全プロパティ・リレーションはオプショナルかデフォルト値／並び順は数値フィールド）
  - レース1—馬券n／収支はレース日基準・未確定は払戻0円・回収率表示
  - 配信は日本限定・年齢レーティングは高め想定

- **購入予定**: MacBook Pro 14インチ・**M5**チップ・**メモリ32GB**・Nano-textureディスプレイ（分割払い）。

## 9. 収益化／お布施の方針

- **大前提**: アプリの機能は**完全無料・無制限**。課金は任意の「お布施（投げ銭／チップ）」のみで、**いかなる機能もゲートしない**（差別化「完全無料・無制限」を崩さない）。
- **スタンス**: 「機能は完全無料。気が向いたら開発を応援（お布施）してね」という位置づけ。
- **実装（IAPを主、外部を補助。併用可）**:
  - **IAPのチップ（主）**: Appleの仕組み内で完結し審査が最も素直。消耗型（Consumable）IAPで300円・600円・1,200円などの金額を用意。手数料はSmall Business Programで**15%**（取り分85%。新規・小規模開発者は対象・要申請）。
  - **GitHub経由（任意・補助）**: アプリ内には「ソースコード（GitHub）」という**中立的なOSSリンクのみ**置き、寄付の訴求はGitHub側のSponsorボタン（FUNDING.yml）に委ねる。Appleの取り分は基本なし（Buy Me a Coffee等の手数料 約5%＋決済）。日本配信なのでスマホ新法下で外部リンク自体は許容される。
- **文言・設計の注意**:
  - チップUIの文言は「開発を応援する」程度に留め、しつこく催促しない。

  - お布施は機能・コンテンツと紐づけない（紐づけると「デジタルコンテンツに関連」扱いとなり外部リンクが使いにくくなる）。
  - 年齢レーティング・「賭け機能なし」の前提は変えない。
